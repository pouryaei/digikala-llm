# راهنمای کامل پیاده‌سازی دستیار حرفه‌ای فروهر

## ۱. هدف و مبنای تغییر

نسخه پایه دقیقاً Forouhar_100K_Final_Best_Model.zip است. فقط یک دستیار
حرفه‌ای و سیاست خودکار داریم؛ هیچ انتخابی بین سه حالت Free/Economic/
Professional به رابط اضافه نشده است. تیک اجازه API صرفاً رضایت برای همان
درخواست است و به معنی اجبار به LLM نیست.

داده ۱۰۰ هزار محصول، ۱٬۸۷۴٬۴۵۷ نظر، نمایه‌های موجود، مدل منتخب
Logistic Regression + Head Fine-tuning و سه مدل مقایسه‌ای حفظ شده‌اند.
گراف موجود توسعه یافته؛ گراف یا برنامه دوم نساخته‌ایم. جست‌وجوی BM25 و
Character TF-IDF فعلی محلی است. ساخت Dense index با Embedding API و
Benchmark زنده مدل‌ها خارج از این اصلاح‌اند.

## ۳. ترتیب اضافه کردن فایل‌ها و اتصالات

### مرحله اول: تنظیمات

requirements.txt فقط وابستگی موجود requirements-llm.txt را نیز نصب می‌کند.
.env.example را از Update بگیرید. اگر .env واقعی دارید آن را پاک یا
جایگزین نکنید؛ فقط تنظیمات تازه را اضافه کنید.

~~~dotenv
QBC13_API_KEY=
QBC13_API_BASE_URL=https://193.93.169.12/v1
QBC13_REVIEW_GENERATION_MODE=extractive

QBC13_ROUTER_MODEL=google/gemini-2.5-flash-lite
QBC13_QA_MODEL=openai/gpt-4o-mini
QBC13_COMPARE_MODEL=openai/gpt-4.1-mini
QBC13_MANAGER_MODEL=openai/gpt-4.1-mini

QBC13_PRO_MAX_ATTEMPTS=2
QBC13_MODEL_TARIFFS_JSON={}
~~~

کلید واقعی گروه را فقط روی سیستم خودتان در .env وارد کنید. مدل‌های بالا
نامزد اولیه هستند، نه برندگان آزمون کیفیت یا قیمت. شناسه‌های مجاز از
فهرست Chat Models اعلام‌شده بوت‌کمپ هستند. تغییر مدل نیاز به تغییر کد
ندارد. QBC13_MODEL_TARIFFS_JSON باید با تعرفه واقعی Gateway به شکل
JSON یک‌خطی پر شود: کلید = شناسه مدل، مقدار = شیء دارای input و output
(دلار به ازای یک میلیون توکن هرکدام). تا قبل از دریافت تعرفه، {} بماند.
قیمت عمومی سازنده را به عنوان تعرفه Gateway فرض نکنید.

### مرحله دوم: bonus/smart_policy.py

کد کامل این فایل را از Update قرار دهید. چهار مسئولیت دارد:

| جزء | ورودی و خروجی | وظیفه |
|---|---|---|
| Decision | stage, mode, reason, model, would_benefit | نتیجه قابل توضیح هر لایه |
| configured_models | متغیرهای محیطی | انتخاب مدل نقش و بررسی شناسه مجاز |
| route_needs_llm / synthesis_value | متن نرمال، intent و context | تعیین ارزش بالقوه با قواعد محلی |
| RequestBudget + BoundedClient | رضایت، کلید، مدل و سقف | کنترل تمام تماس‌ها و شمارش مصرف |

در این سیاست مدل زبانی تصمیم نمی‌گیرد که آیا باید مدل دیگری صدا شود.
مسیر با قواعد و انتخاب صریح کاربر آغاز می‌شود. تابع route_needs_llm
در صورت تعارض نشانه‌های دو هدف یا درخواست طولانی بدون نشانه روشن،
ارزش احتمالی رفع ابهام را گزارش می‌کند. این heuristic است نه نمره
احتمالی یا تضمین صحت. هدف صریح، دسته معلوم، شناسه‌ها و سؤال عددی مستقیم
معمولاً هزینه مسیریاب را حذف می‌کنند.

RequestBudget.choose به ترتیب کفایت شاهد، ارزش افزوده، مجوز، وجود
کلید/مدل معتبر و تلاش باقی‌مانده را بررسی می‌کند. اگر هر شرط لازم برقرار
نباشد نتیجه local است. برای مرحله Router، ابهام متن ورودی معیار اصلی
است و نیازی به بازیابی شاهد محصول ندارد.

یک RequestBudget به ازای هر درخواست ساخته می‌شود. BoundedClient یک
آداپتور برای LLMClient موجود است. قبل از generate تلاش را رزرو می‌کند؛
خطا هم تلاش محسوب می‌شود. LLMClient با max_retries=1 و SDK با
max_retries=0 اجرا می‌شوند. در صورت درخواست اصلاح JSON یا ارجاع از
LLMService، همین بودجه دوباره بررسی می‌شود.

| محدودیت | مقدار |
|---|---|
| سقف مشترک همه لایه‌ها و repair | 2 تلاش برای هر درخواست |
| سقف تقاضای خروجی Router | 150 Token |
| سقف تقاضای خروجی QA/Compare/Manager | 350 Token در هر تلاش |
| سقف متن ورودی هر تلاش | 10000 کاراکتر شامل Prompt |

سقف تعداد تلاش، سقف دلاری قطعی کل پروژه نیست. هزینه با usage واقعی و
تعرفه هر مدل گزارش می‌شود. اگر تعرفه یا usage ناقص باشد هزینه نامعلوم
است؛ اگر هیچ تلاش تازه‌ای انجام نشود هزینه همان اجرا صفر است.

### مرحله سوم: bonus/professional.py

این فایل از Workflow موجود ارث می‌برد و همان گراف واقعی LangGraph را
با nodeهای قبلی اجرا می‌کند. در صورت نبود LangGraph، مسیر Python قبلی
با برچسب واقعی اجرا می‌شود. کد کامل در ZIP است.

~~~text
run(request)             اعتبارسنجی و ساخت بودجه مشترک
    └── route_intent     کش کامل → مسیریاب محلی → Router اختیاری
        └── cache_lookup
            ├── HIT → finalize
            └── شاخه تخصصی محلی
                ├── search
                ├── qa_resolve → qa_retrieve → qa_policy
                │       ├── qa_extractive / qa_insufficient
                │       └── qa_generate → qa_validate → fallback در خطا
                ├── compare → مکمل اختیاری مستند
                ├── manager → مکمل اختیاری مستند
                ├── predict / audit / clarify
                └── finalize → پاسخ، cache و Trace
~~~

#### ۳.۱. _route: کش قبل از تصمیم

request_fingerprint کلید هش‌شده را از query دقیق، intent، شناسه‌ها،
category، filters، retrieval_mode، نسخه سیاست، شناسه مدل‌ها، سقف
تلاش، نسخه کاتالوگ، وضعیت فایل‌های داده/نمایه و واحد قیمت می‌سازد.
اگر نسخه فایل‌ها قابل بررسی نباشد، نتیجه cache نمی‌شود.

اگر پاسخ کاملِ پذیرفته‌شده در کش باشد هیچ تماس تازه‌ای انجام نمی‌شود.
اگر پاسخ کامل نباشد، classify_intent موجود مسیر محلی را تعیین می‌کند.
فقط برای ابهام قابل رفع، مدل Router انتخاب می‌شود. خروجی آن JSON دارای
intent در allowlist ثابت است. مدل حق ساخت شناسه یا بازنویسی فیلتر و حذف
محدودیت کاربر را ندارد. انتخاب صریح کاربر همیشه مقدم است. خروجی نامعتبر
به همان مسیر محلی برمی‌گردد. مسیر پذیرفته‌شده نیز جدا cache می‌شود.

#### ۳.۲. Search: سرویس بازیابی موجود

_search همان bonus.retrieval.search را فراخوانی می‌کند. فیلترها
و سیاست BM25/Hybrid قبلی حفظ شده‌اند. تولید زبانی جایگزین بازیابی
نیست. استفاده از API برای Embedding یک آزمایش جداگانه خواهد بود.

#### ۳.۳. QA: شواهد واقعی، سپس انتخابی LLM

qa_resolve و qa_retrieve همان کد موجود هستند. _qa_policy از تابع
generation_policy موجود استفاده می‌کند، ولی ابتدا کفایت شاهد، پوشش
موضوع‌های سؤال، تعداد نظر مستقل و نیاز به جمع‌بندی را مستقل از
مجوز بررسی می‌کند. برای تولید زبانی حداقل دو نظر مستقل، پوشش معیارها
و نیاز به ترکیب شواهد لازم است. پاسخ آماری ساده و کمبود شاهد پولی نیست.

_qa_generate یک BoundedClient با نقش qa به LLMService می‌دهد.
این سرویس فقط سؤال و نظرهای بازیابی‌شده را به مدل منتخب می‌دهد.
_qa_validate از validatorهای قبلی برای بررسی شناسه و نقل‌قول دقیق
استفاده می‌کند و در صورت عدد بدون پشتوانه نقل‌قول، مکمل رد می‌شود.
اگر مدل اشتباه پاسخ دهد، متن و شواهد استخراجی محلی حفظ می‌شوند.

#### ۳.۴. Compare: اطلاعات هر محصول + توضیح اختیاری

_compare ابتدا src.rag.compare_products موجود را اجرا می‌کند. اگر
سؤال ساده است، facts، review_stats و comparison_notes کافی هستند.
اگر درخواست جمع‌بندی/تفسیر دارد و برای همه محصول‌ها facts و نظر مرتبط
وجود دارد، comparison_sources تعداد محدودی منبع با source_id ارائه
می‌کند. مدل نقش compare فقط روی این منابع تفسیر می‌دهد. validate_synthesis
شناسه، نقل‌قول دقیق، اعداد و پوشش همه محصولات را بررسی می‌کند.
خروجی پذیرفته‌شده در professional_synthesis قرار می‌گیرد؛ جدول محلی
بدون تغییر باقی می‌ماند.

#### ۳.۵. Manager: محاسبه با DuckDB

_manager از manager_analytics.answer_manager_question استفاده می‌کند.
Query SQL از LLM دریافت نمی‌شود. manager_sources فقط آمار واقعی،
خلاصه، حداکثر هشت ردیف و چند شاهد کوتاه را جمع می‌کند. اگر درخواست
تحلیل، دلیل یا پیشنهاد بهبود باشد، مدل manager در صورت کفایت داده و
مجوز وارد می‌شود. همان اعتبارسنجی Compare انجام می‌شود. مدل تنها تفسیر
می‌دهد و نه محاسبه عدد تازه.

#### ۳.۶. Predict / Audit / Clarify

پیش‌بینی با ml_service.py و Head Fine-tuning موجود انجام می‌شود.
audit از محاسبات آماری موجود کمک می‌گیرد و clarify از کاربر اطلاعات
تکمیلی می‌خواهد. این سه شاخه تولید زبانی اجباری ندارند.

### مرحله چهارم: cache و monitoring

ResultCache موجود دوباره استفاده شده: حافظه موقت همان نشست Streamlit،
TTL=600 ثانیه، ظرفیت 128. کش پاسخ و کش مسیر جدا هستند. تغییر نسخه
داده/index/model باعث عدم تطابق کلید می‌شود. اندازه/mtime و manifest
کنترل تغییر نسخه‌اند؛ اگر داده عمداً تغییر داده شود manifest و نمایه
را نیز بازسازی یا برنامه را restart کنید.

پاسخ نامعتبر، شکست مدل، سؤال بی‌پاسخ و پاسخ ناقصی که به‌علت نبود
مجوز/کلید/بودجه ارتقا نیافته است به عنوان پاسخ کامل ذخیره نمی‌شود.
پیش‌بینی متن خصوصی نیز cache نمی‌شود. پاسخ پذیرفته‌شده قبلی را حتی
بدون مجوز تماس جدید می‌توان از کش خواند؛ UI منشأ را نشان می‌دهد.
Token و هزینه قبلی به عنوان تماس تازه شمارش نمی‌شوند.

graph.py فقط از دوباره‌شماری usage در span قدیمی QA جلوگیری می‌کند؛
BoundedClient برای هر تلاش واقعی span جداگانه professional_llm_<role>
می‌سازد. observability.py فیلدهای مجاز تصمیم‌ها، مدل، زمان و شمارش را
در TraceStore قبلی اضافه می‌کند. کلید، متن سؤال، Prompt و متن نظر در
Trace ذخیره/صادر نمی‌شوند. فعال‌سازی سرور Langfuse مستقل و اختیاری است.

### مرحله پنجم: اتصال UI

در app.py دکمه دستیار حرفه‌ای اضافه شده و همان زیرتب مسیریاب و
مانیتورینگ را باز می‌کند:

~~~python
def open_professional():
    st.session_state["main_tabs"] = MAIN_TABS[3]
    st.session_state["bonus_lab_tabs"] = "مسیریاب و مانیتورینگ"
~~~

در bonus/dashboard.py، router_panel از کلاس ProfessionalWorkflow
به جای ایجاد Workflow قدیمی استفاده می‌کند. اتصال اصلی:

~~~python
entry = ProfessionalWorkflow(
    cache=st.session_state["professional_session_cache"]
).run({
    "query": q,
    "intent": mode,
    "product_ids": parsed,
    "category": cat.strip() or None,
    "retrieval_mode": "auto",
    "use_cache": cache,
    "allow_llm": live,

~~~

mode فقط نوع درخواست است، نه سطح هزینه. انتخاب هدف اختیاری و به
صرفه‌جویی کمک می‌کند. گزینه API پیش‌فرض خاموش است. جدول هر مرحله،
مسیر گراف، Cache HIT، مدل، تعداد تلاش مصرف‌شده، Token و برآورد هزینه
نمایش داده می‌شوند. در src/dashboard_rag.py مسیر مستقیم QA صریحاً
extractive است تا تنظیم قدیمی .env باعث تماس پولی خارج از بودجه مشترک
نشود. تب‌های تخصصی قدیمی مسیر محلی سریع‌اند. هیچ نیازی به سه UI یا سه
pipeline جداگانه نیست.

reports/bonus/professional_policy.json است.

## ۴. نصب و اجرای عملی

دو راه دارید. اگر نسخه کامل Professional را دارید، آن را در یک پوشه
تازه استخراج کنید. اگر از Update استفاده می‌کنید، فایل‌های آن را دقیقاً
روی ریشه Forouhar_Bonus در نسخه پایه استخراج و جایگزین کنید (داخل
پوشه دیگر نسازید). فایل واقعی .env شما در Update نیست. از قبل پشتیبان
بگیرید و اجرای قبلی را با Ctrl+C متوقف کنید. در VS Code از پوشه با app.py:

~~~powershell
python -m pip install -r requirements.txt
python -m pip install pytest
python -m pytest -q tests/test_professional.py tests/test_bonus_ui.py
.\RUN_FOROUHAR_FINAL.bat
~~~

آدرس: http://localhost:8505؛ دکمه «دستیار حرفه‌ای · انتخاب خودکار مدل».
برای آزمایش بدون هزینه، گزینه مجوز API خاموش باشد. برای دیدن Cache HIT
همان درخواستِ کاملِ موفق را در همان نشست تکرار کنید.

تست CLI آفلاین:

~~~powershell
python -X utf8 -m bonus.professional --intent qa --product-id 1696173 --query "چند نفر خرید این محصول را پیشنهاد کرده‌اند؟"
~~~

بازتولید ارزیابی ده سناریو:

~~~powershell
python -X utf8 -m bonus.evaluate_professional
~~~

تست واقعی (فقط بعد از بررسی تعرفه و وارد کردن کلید محلی) با اضافه کردن
--live به درخواست دارای شواهد کافی:

~~~powershell
python -X utf8 -m bonus.professional --intent qa --product-id 1696173 --query "کیفیت ساخت و راحتی این محصول را با استناد به تجربه کاربران جمع‌بندی کن." --live
~~~

--live مجوز همان درخواست و حداکثر دو تلاش است؛ تضمین هزینه دلاری نیست.
در صورت خطای ارتباط/TLS، از مسئول درگاه تنظیمات صحیح را بگیرید و
اعتبارسنجی TLS را غیرفعال نکنید. CLI در هر اجرا cache جدید دارد.

## ۵. دفاع و محدودیت‌ها

در اجرای کنترل‌شده ده سناریو، ۶ درخواست اول بدون تلاش زبانی، مجموع ۵
تلاش شبیه‌سازی‌شده در اجرای اول، صفر تلاش جدید در تکرار، ۶ HIT کش کامل
و حفظ داده محلی در ۱۰/۱۰ مورد ثبت شد. گزارش دقیق همراه بسته است.
این آزمایش فقط تصمیم‌ها، قرارداد و کنترل هزینه/کش را می‌سنجد؛ اثبات
کیفیت واقعی مدل‌ها و صرفه‌جویی دلاری نیست. اعتبارسنجی ارجاع، عدد و
نقل‌قول نیز جای ارزیابی معنایی را نمی‌گیرد. اتصال واقعی با کلید گروه،
مقایسه کیفیت/سرعت/قیمت نامزدها، و تأیید ارسال به سرور Langfuse همچنان
به محیط و کلید شما نیاز دارند. هیچ اسلایدی تولید نشده و هیچ تماس پولی
به درگاه صورت نگرفته است.
